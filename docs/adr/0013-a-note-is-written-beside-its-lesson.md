# A note is written beside its lesson

*Revised by ADR-0014: the note, the Markdown and the transcript file now go to a build directory rather than beside the lesson. The argument below — that a destination directory was the obvious alternative and was rejected — is the one that decision answers, and it is kept for that reason.*

`build` has printed the note it would create as a one-line JSON document on stdout, and it now writes it instead: `englishpod_C0108.json` beside `englishpod_C0108.md`, named for the lesson code the note is identified by, and stdout carries the path rather than the document. The stage exists so a lesson can be looked at without touching Anki, and until now the only way to look at one twice was to run it twice — the design's cheap check cost a dictionary lookup every time it was made, and a run with one dictionary unreachable that day would answer differently from the run before it. The learner's own words for it were the ordinary ones: they built a lesson, wanted to keep what they saw, and copied it out of the terminal. A file is what a person can read back, diff, and keep.

It goes beside the lesson rather than somewhere named on the command line, and that is the decision most worth writing down here, because a destination directory was the obvious alternative. Every stage in this tool takes one positional path and derives everything else from it: `preprocess` writes its Markdown beside the PDF, the transcript file goes beside the Markdown, and the corpus's layout is the only index the tool keeps. A `--dest` would be the first directory-valued flag in the tool and the first place the corpus's shape stopped deciding anything — and pointed at the corpus, it would either mirror three hundred directories or flatten three hundred notes into one, neither of which is the thing anybody wants. Beside the lesson, a note travels with the lesson: move the corpus, copy one lesson somewhere, and what was written about it is still there and still about it.

The file is written over, every run, with no flag to ask and none to refuse. `preprocess` guards its Markdown with `--force`, and the difference between the two files is the whole reason: the Markdown is source, corrected by hand, and a run that overwrote it would destroy work. The note is a report — derived from the Markdown, holding nothing the Markdown does not, and read back by nothing — so a run that left it alone when it already existed would leave a note beside a corrected Markdown that no longer matched it, which is the one thing it must not do. The cost is real and accepted: a hand-edited note file is lost on the next build. It was never going to be kept, since nothing reads it back, and the Markdown and the transcriptions file are where a person's corrections belong and are read.

Written as a person reads it rather than as a shell consumes it: indented over its lines, with the IPA literal rather than escaped as `ˈ`, which the old one-line form had to do only because a terminal was the medium. The write goes beside the file it replaces and is then moved over it, so a run stopped in the middle of one leaves the note it found where it was — the idiom `transcription.py` already uses for its file, and the only atomic write in the tool. This is deliberately the one place the tool does more than `preprocess` does for its Markdown, which is written plainly: a truncated Markdown is visibly truncated and a person is looking at it, while a truncated JSON document is one an editor or a script would report as malformed with nothing to say about why.

A note that cannot be written is a lesson the run skips and names, and a run that wrote nothing at all exits non-zero. This is where the note file differs from the transcriptions file, which reports its own failure once and costs a lookup, and the reason is what each one is. That file is a cache whose failure is deferred; the note file is the whole of what `build` leaves behind. A summary reading "365 lessons: 365 built" while some of them have no file on disk is the kind of thing this tool's reports exist not to say, so the writer raises the error `read_markdown` raises for the same reason, `corpus.run` skips the lesson, and the skip line names the path and the reason — `cannot write /path/englishpod_C0297.json: Permission denied`.

Three alternatives were set aside. Keeping the shell-redirect workflow (`build /path/to/corpus > notes.jsonl`) and documenting it better is what the tool did until now, and it puts three hundred notes in one file that nothing can attribute to a lesson without reading the line; a corpus keeps its notes apart, the way it keeps everything else. A `--dest` directory was rejected above. And writing an `.apkg` — a file Anki itself can read — stays rejected for the reason ADR-0001 gives: a file-based handoff leaves the import blind to what the collection already holds, and this change does not touch that. What it does not change is that `import` never reads the note file: it builds the note again from the same Markdown, because the card is what matters and the file is only how a person looks at it.
