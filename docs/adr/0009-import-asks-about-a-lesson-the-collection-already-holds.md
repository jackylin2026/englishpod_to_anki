# Import asks about a lesson the collection already holds

Before it writes a note, import reads the deck it is writing into and looks for one that already stands for the lesson in hand. Finding one, it asks: leave that note exactly as it is, or refresh its content and keep everything else about it. Nothing is written until the question is answered. One answer can be given for every lesson left in the run — `s all`, `r all` — and `--existing skip` or `--existing replace` answers ahead of time, so a scripted run never waits on a prompt it cannot answer.

The tool must not decide this for the learner. The note already there may be one they have studied for months, and the two answers fail in opposite directions: skipping leaves a card built from an older parser, and replacing writes over content they may have corrected by hand. Deciding by flag alone, with no question, was the alternative and is rejected for exactly that reason — a tool that silently leaves three hundred stale cards, or silently rewrites three hundred studied ones, is worse in both directions than one question. Asking costs a stalled script the first time someone forgets the flag, so a run with nobody to answer says what it was asked and what to pass rather than waiting on an answer that will not come.

Replace is `updateNoteFields` on the note that is there, and nothing else. It is never a deletion and a note made again: Anki's note ids and guids are not reproducible by this tool (ADR-0004), and a note made again is a card the learner has never studied, in place of one they have. The scheduling and the review history are the whole reason the question exists, so the answer called replace cannot be the one thing that discards them.

A lesson is recognised as already present in two ways, because the learner's collection predates the tool. The first is the tag `englishpod::C0108` that a note made by the tool carries — the note's identity (ADR-0004), and what a later run is meant to find it by. The second is the dialogue: a note in the deck, of any note type, whose `Sentences` field holds the lesson's own words. The learner's profile holds 102 EnglishPod notes made by hand before this tool existed, and those carry no tags at all, so a tag search alone would call every one of them absent and hand them a second card for a lesson they had studied. Comparing the dialogue rather than the card is what makes the match possible: a hand-made card blanks the words its maker wanted to practise — seven of the thirteen lesson 108 supports (ADR-0003) — while the tool blanks the lesson's whole Key Vocabulary, so the two cards are the same lesson and not the same text. Taking the blanks, the line breaks and the punctuation out of both, and comparing the words that are left, is what the two have in common. Punctuation is part of it because the learner's own cards are not punctuated the way the extraction punctuates: `Don’t` against `Dont`, `....` against `. . . .`, `” Fun` against `”Fun`, and `partly-cloudy` against `partlycloudy` are all the same words said the same way, and all four were cards the first cut of this missed.

Measured against the learner's collection, 48 of the 102 cards it holds are recognised by their dialogue — the reference card for lesson 108 among them, which blanks seven of that dialogue's words where the tool blanks eleven. The rest are lessons the tool cannot build yet, nearly all of them the image-only scans that want the OCR pass (#7), so their lessons are never imported and never duplicated; five are cards whose dialogue was edited to different words (`daughter` where the lesson says `son`, a first turn left off), and those lessons import a second card. Two notes holding the same dialogue are taken as one lesson — the first found — with nothing said about the second.

Two things are reported rather than decided. A lesson the collection holds twice — two notes carrying one `englishpod::` tag — is left alone with the lesson named, since which of them is the lesson's note is not the tool's to guess. And a note found by its dialogue is only written into when the note type holding it renders the card, checked exactly as the tool's own note type is (ADR-0005): a hand-made card under a type that renders no glossary is left as it is, because writing the glossary into it would put it where nobody will ever see it. Both are reported the way any lesson the run cannot work with is, and the run carries on — neither is a reason to stop the other three hundred lessons, which is what stopping the run would do.

A lesson left as it is counts as work. It was looked at and settled, so a corpus-wide `--existing skip` over a collection that already holds every lesson exits zero and says how many were left, where a run over the same corpus that skipped every lesson for reasons of its own still exits non-zero (ADR-0006). A run whose every lesson failed to build or to read is a run that did nothing, and still says so with its exit code.

The cost is one read of the deck before the first note is written: every note in the deck, with its tags and its fields, fetched once a run. That is what makes a corpus-wide run affordable — the alternative is asking about the same collection once per lesson — but it does mean that a very large deck is a very large read, and that the run sees the collection as it stood when it started: a note another program adds mid-run is not one this run will recognise.
