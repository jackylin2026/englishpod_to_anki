# Import asks about a lesson the collection already holds

Before it writes a note, import reads the deck it is writing into and looks for one that already stands for the lesson in hand. Finding one, it asks: leave that note exactly as it is, or refresh its content and keep everything else about it. Nothing is written until the question is answered. One answer can be given for every lesson left in the run — `s all`, `r all` — and `--existing skip` or `--existing replace` answers ahead of time, so a scripted run never waits on a prompt it cannot answer.

The tool must not decide this for the learner. The note already there may be one they have studied for months, and the two answers fail in opposite directions: skipping leaves a card built from an older parser, and replacing writes over content they may have corrected by hand. Deciding by flag alone, with no question, was the alternative and is rejected for exactly that reason — a tool that silently leaves three hundred stale cards, or silently rewrites three hundred studied ones, is worse in both directions than one question. Asking costs a stalled script the first time someone forgets the flag, so a run with nobody to answer says what it was asked and what to pass rather than waiting on an answer that will not come.

Replace is `updateNoteFields` on the note that is there, and nothing else. It is never a deletion and a note made again: Anki's note ids and guids are not reproducible by this tool (ADR-0004), and a note made again is a card the learner has never studied, in place of one they have. The scheduling and the review history are the whole reason the question exists, so the answer called replace cannot be the one thing that discards them.

A lesson is recognised as already present in three ways, looked for in this order, because the learner's collection predates the tool. The first is the tag `englishpod::C0108` that a note made by the tool carries — the note's identity (ADR-0004), and what a later run is meant to find it by. The second is the dialogue recording the note plays: its `TTS` field holds `[sound:englishpod_D0108dg.mp3]`, the corpus attaches that file under the name it was downloaded with, and no two lessons were recorded into one file — so the field names the lesson exactly, and names it even when the note is worded quite unlike the lesson's own text. The third is the dialogue itself: a note in the deck, of any note type, whose `Sentences` field holds the lesson's own words.

The learner's profile holds 102 EnglishPod notes made by hand before this tool existed, and those carry no tags at all, so a tag search alone would call every one of them absent and hand them a second card for a lesson they had studied. The recording is what finds them: all 102 play the corpus's own dialogue audio, and 48 of them hold the lesson's words as well. The words are compared, rather than the cards, because a hand-made card blanks the words its maker wanted to practise — seven of the thirteen lesson 108 supports (ADR-0003) — while the tool blanks the lesson's whole Key Vocabulary, so the two cards are the same lesson and not the same text. Taking the blanks, the line breaks, the punctuation and the escaping out of both, and comparing the words that are left, is what the two have in common. Punctuation is part of it because the learner's own cards are not punctuated the way the extraction punctuates: `Don’t` against `Dont`, `....` against `. . . .`, `” Fun` against `”Fun`, and `partly-cloudy` against `partlycloudy` were each a card the first cut of this missed. The escaping is part of it because one lesson's text layer prints `&quot;`, which its card then holds doubly escaped — `&amp;quot;` — where a card made by hand from the same dialogue holds the character itself.

Measured against the collection, every one of the 102 cards is recognised: 101 of them by the recording they play, and the one whose card plays no recording by its words. The reference card for lesson 108 is among them — it blanks seven of that dialogue's words where the tool blanks eleven. End to end over the learner's corpus, against a stand-in collection holding those 102 notes: `import: 365 lessons: 181 imported, 102 left as they were, 82 skipped`, and not one write to a note that was already there. Matching on the tag and the words alone — the first shape of this — recognised 48, and would have cost a second card for each of the other 54: their dialogue differs from the corpus's own text by a word or two (`religous` for `religious`, `daughter` for `son`, a `today` moved), and no rule for comparing words that could tell those apart from another lesson's would be worth having. The recording is what makes the difference: it is the corpus's own name for the lesson, not a likeness of its text.

Two notes holding the same dialogue are taken as one lesson — the first found — with nothing said about the second.

Two things are reported rather than decided. A lesson the collection holds twice — two notes carrying one `englishpod::` tag — is left alone with the lesson named, since which of them is the lesson's note is not the tool's to guess. And a note found by its dialogue is only written into when the note type holding it renders the card, checked exactly as the tool's own note type is (ADR-0005): a hand-made card under a type that renders no glossary is left as it is, because writing the glossary into it would put it where nobody will ever see it. Both are reported the way any lesson the run cannot work with is, and the run carries on — neither is a reason to stop the other three hundred lessons, which is what stopping the run would do.

A lesson left as it is counts as work. It was looked at and settled, so a corpus-wide `--existing skip` over a collection that already holds every lesson exits zero and says how many were left, where a run over the same corpus that skipped every lesson for reasons of its own still exits non-zero (ADR-0006). A run whose every lesson failed to build or to read is a run that did nothing, and still says so with its exit code.

The cost is one read of the deck before the first note is written: every note in the deck, with its tags and its fields, fetched once a run. That is what makes a corpus-wide run affordable — the alternative is asking about the same collection once per lesson — but it does mean that a very large deck is a very large read, and that the run sees the collection as it stood when it started: a note another program adds mid-run is not one this run will recognise, and a note it removes between the search and the read answers with nothing, which the run reads past rather than falling over.
