# A note's identity is a tag carrying the lesson code

Every note is born carrying a tag of the form `englishpod::C0108`, built from the lesson code read from inside the lesson. A later run finds the note an earlier run made by searching the collection for that tag, rather than by remembering a note id or by hunting for a matching first field.

A deterministic identity is required because the tool is run repeatedly against an evolving corpus, and a run that cannot find what it made cannot skip it or refresh it. Anki's own identities cannot serve: a note's guid is computed by Anki at insertion time and is unreproducible — the hand-built card's is `vi~g!-uKUB`. AnkiConnect offers no way to set one; its `addNote` takes a deck, a note type, fields and tags, and nothing else. Of those four, only a tag can carry a value the tool chooses, be searched for with `findNotes`, and stay invisible on the card the learner studies. The value is the lesson code because that is the corpus's own name for a lesson, the one identifier every stage already reads and the one a person would search for by hand.

Holding the identity in a field was the alternative, and it is rejected because the card's six fields are the design: an id field would be a seventh field, visible in the note editor and carried by every card forever, to serve a bookkeeping need that a tag serves invisibly. A mapping file beside the corpus was the other, and it is rejected because it puts the answer outside the collection it describes: it goes stale the moment notes are added, moved or deleted by hand, and Anki is the only place that knows what Anki holds.

The cost is a tag the learner did not choose appearing in their collection, and a small vocabulary of tool-owned tags that must not collide with their own — which is what the `englishpod::` prefix is for. It also gives a way to find every note the tool has made, which is what the next run needs when it must decide, lesson by lesson, what to do about the ones already there.
