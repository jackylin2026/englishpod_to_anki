# The tool's own files go to a build directory

Every file the tool wrote about a lesson was written *into the corpus*: `preprocess` put `englishpod_<code>.md` beside the lesson's PDF and the print transcript's version of the dialogue beside that, and ADR-0013 put `build`'s note file beside the Markdown. The corpus is supposed to be read where it lies, and it no longer was. The learner's own copy is 296 Markdowns and 296 transcript files among the PDFs and recordings, which makes two things harder than they should be: telling at a glance what came with the corpus and what the tool made, and finding everything the tool made about a lesson in one place. They now go to a **build directory**, one subdirectory to a lesson, and the corpus is never written into at all.

The subdirectory is named for the lesson's *directory* in the corpus — `build/0297/` for `.../0291-0300/0297/` — and the Markdown inside it for the code the document prints, `englishpod_C0297.md`. That split is the whole of why the layout works, and it is worth being exact about. A stage is often pointed at a corpus directory and needs the build directory for each lesson in it before it has read a single document; what it knows at that moment is the lesson's path, and the path ends in a number. So the subdirectory is the path-derived name and the file is the code-derived one, and both stages that need the layout — the one that writes and the two that read — compute it the same way. Every lesson directory in the corpus is its own number, 365 of them and no two alike, so nothing collides, and a lesson not yet preprocessed has no code for anything to be named after yet anyway.

ADR-0013 argued against a destination directory and this decision must answer it rather than pretend it was never weighed. Its case was that a directory-valued flag would be "the first place the corpus's shape stopped deciding anything", and that pointed at a corpus it would either mirror three hundred directories or flatten three hundred notes into one. The first concern is answered by there being no flag: where the build directory is comes from `ENGLISHPOD_BUILD_DIR` in the environment or in the `.env` the tool already reads its OCR credentials from, falling back to a `build/` under wherever the tool was run. A run has nothing to pass and nothing to remember, and the corpus's shape still decides everything about what a lesson's files are called. The second concern is answered by the layout above: the build directory *does* mirror the corpus's lesson directories, one for one, which is the arrangement 0013 described as the worse of the two and which turns out to be the one that costs nothing — the mirroring is by name, not by path, so it is flat, and a lesson's own number is the name it already has.

What is deliberately *not* copied is the recordings. The build directory holds text alone: the Markdown, the note file, and the transcript file. A note's audio path already points into the corpus and is absolute — the card plays the recording where the corpus keeps it — so copying it would add 365 binaries to keep in step with the originals for no gain. The cost is real and accepted: a card whose corpus has been moved or deleted loses its sound, and the note file says which file it wanted.

Two rules about the Markdown itself had to be settled again, because the file it is written to is chosen differently. The check for an existing Markdown happens *before* the PDF is read, not after: reading a page is what the OCR pass is paid for, and a lesson already written is a lesson with nothing to read it for. And when a run does write — because there was no Markdown, or because `--force` — the file that is there is the file it writes back to, whatever it is called, so that a lesson holds one Markdown and not a second one beside it. A forced run that finds the file named for a code the document does not print writes the code-derived name and takes the other away, since a file no later run would look for is worse than no file at all.

A note that cannot be written is a lesson the run skips and names, which is ADR-0013's decision and stands. The build directory itself is made when it is not there rather than asked for, and a lesson whose Markdown was never written is skipped with a reason that names the stage that would have written it — `has no Markdown in <build dir>; run preprocess on it first` — because that is now a thing a run can meet, where before the Markdown was beside the lesson or it was not.

The walk over a corpus passes the build directory by, when a run keeps it inside the corpus. A lesson is recognised by the files a directory holds, and one of them is a Markdown; a build subdirectory holds a Markdown and no PDF, which is exactly the shape of a lesson whose PDF has been lost. Left in the walk it would be reported as one more unreadable lesson per lesson, so `corpus.lessons` is given the build root and skips it by resolved path, as it skips what `.englishpodignore` names and for the same reason: a directory that is not a lesson should not have to be explained away in the report.

The corpus this was measured against holds 296 Markdowns from the old layout, and the migration is real work rather than a detail: `scripts/move_to_build.py` moves each one into its lesson's subdirectory, renaming it for the code it carries where that differs from the name it has — `englishpod_D0108.md` becomes `englishpod_C0108.md` — and leaving the name alone where the Markdown carries no code, since there is nothing to name it after. It is a script and not a stage because it runs once, against one corpus, and a tool that carries a migration forever is a tool with a stage nobody should ever run again.
